Almost every Salesforce screen is a form: create a record, edit it, validate it, show errors. Lightning Web Components give you three layers for this, from ready-made forms to full control through the UI API. Choosing the right layer saves a lot of code.

## The business scenario

Juniper Consulting's service team creates Cases from a custom "Quick Case" panel on the Account page. They want the Account to be prefilled, the Priority picklist to show only valid values, a subject of at least 10 characters, a rule that "High" priority cases need a description, a toast on success, and a clean error message when Salesforce rejects the save. A stock page layout cannot enforce the description rule in the panel the way the team wants, so you will build the form yourself.

## Before you start: setup

### In Salesforce

1. Use a Developer Edition org or sandbox with the Salesforce CLI and VS Code Salesforce extensions; connect with `sf org login web --alias dev`.
2. Create a Salesforce DX project and set `"sourceApiVersion": "67.0"`.
3. In **Object Manager, Case**, confirm the Priority picklist has values (Low, Medium, High) and that **Subject** and **Description** are visible to your profile. Check field-level security: the form shows only fields the user can see.
4. Optionally create a **validation rule** on Case: `AND(ISPICKVAL(Priority,"High"), ISBLANK(Description))` with the message "High priority cases need a description." Client checks improve the experience, but **server rules remain the real enforcement**.
5. Give your users a permission set with Create on Case and Read on Account.
6. For tests, install Jest tooling: `npm install` in the project, which includes `@salesforce/sfdx-lwc-jest` when the project was generated by the CLI. Run with `npm run test:unit`.
7. Add the component to the Account record page in **Lightning App Builder** (the meta file below exposes it).

### In the external system

None. If the form should also create a record in an external system, do that in an Apex action called after the save, through a Named Credential, and never from the browser.

## How it works

Three layers:

1. **`lightning-record-form`**: one tag, whole form. Quickest, least control.
2. **`lightning-record-edit-form`** with **`lightning-input-field`**: you control layout and buttons; Salesforce provides field rendering, picklists, required indicators, field-level security and server errors.
3. **UI API adapters** (`createRecord`, `updateRecord`, `getObjectInfo`, `getPicklistValues`, `getRecord` from `lightning/uiRecordApi` and `lightning/uiObjectInfoApi`): full control. You render inputs yourself and call the adapters to save.

The deciding questions: do you need a custom layout or only standard fields? Layer 2. Do you need to compute values, validate across fields or use `lightning-input` for custom controls? Layer 3.

**Validation** has two sides. Client checks use the browser, `setCustomValidity` and `reportValidity()` on `lightning-input`. They give instant feedback. Server checks (validation rules, triggers, required fields) always run, and their messages arrive as errors you must display.

## Basic example

Layer 2, standard fields, almost no JavaScript.

```html
<template>
  <lightning-record-edit-form
    object-api-name="Case"
    onsuccess={handleSuccess}
    onerror={handleError}>
    <lightning-messages></lightning-messages>
    <lightning-input-field field-name="AccountId" value={recordId}></lightning-input-field>
    <lightning-input-field field-name="Subject"></lightning-input-field>
    <lightning-input-field field-name="Priority"></lightning-input-field>
    <lightning-input-field field-name="Description"></lightning-input-field>
    <lightning-button type="submit" label="Create case" variant="brand"></lightning-button>
  </lightning-record-edit-form>
</template>
```

```javascript
import { LightningElement, api } from 'lwc';
import { ShowToastEvent } from 'lightning/platformShowToastEvent';

export default class QuickCaseBasic extends LightningElement {
  @api recordId;

  handleSuccess(event) {
    this.dispatchEvent(new ShowToastEvent({
      title: 'Case created',
      message: 'Case ' + event.detail.id + ' was saved.',
      variant: 'success'
    }));
  }

  handleError(event) {
    console.error(JSON.stringify(event.detail));
  }
}
```

`lightning-messages` shows server errors automatically, including validation rule messages. This is already good enough for many cases.

## Advanced end-to-end example

Layer 3, with a validation module that is easy to test, picklist values loaded from the schema, and a clean error path.

**force-app/main/default/lwc/quickCase/caseRules.js**

```javascript
export const MIN_SUBJECT_LENGTH = 10;

// Returns an object of { fieldName: message }. Empty object means valid.
export function validateCase(values) {
  const errors = {};
  const subject = (values.subject || '').trim();
  if (subject.length < MIN_SUBJECT_LENGTH) {
    errors.subject = `Subject needs at least ${MIN_SUBJECT_LENGTH} characters.`;
  }
  if (!values.priority) {
    errors.priority = 'Choose a priority.';
  }
  if (values.priority === 'High' && !(values.description || '').trim()) {
    errors.description = 'High priority cases need a description.';
  }
  return errors;
}

// Turns UI API / Apex errors into one readable string.
export function readError(error) {
  if (!error) {
    return 'Unknown error';
  }
  const body = error.body;
  if (Array.isArray(body)) {
    return body.map(e => e.message).join(', ');
  }
  if (body && body.output && Array.isArray(body.output.errors) && body.output.errors.length > 0) {
    return body.output.errors.map(e => e.message).join(', ');
  }
  if (body && typeof body.message === 'string') {
    return body.message;
  }
  return typeof error.message === 'string' ? error.message : 'Unknown error';
}
```

**force-app/main/default/lwc/quickCase/quickCase.js**

```javascript
import { LightningElement, api, wire } from 'lwc';
import { createRecord } from 'lightning/uiRecordApi';
import { getObjectInfo, getPicklistValues } from 'lightning/uiObjectInfoApi';
import { ShowToastEvent } from 'lightning/platformShowToastEvent';
import CASE_OBJECT from '@salesforce/schema/Case';
import PRIORITY_FIELD from '@salesforce/schema/Case.Priority';
import { validateCase, readError } from './caseRules';

export default class QuickCase extends LightningElement {
  @api recordId; // the Account Id when placed on an Account page

  values = { subject: '', priority: '', description: '' };
  errors = {};
  saving = false;
  serverError = '';
  priorityOptions = [];

  @wire(getObjectInfo, { objectApiName: CASE_OBJECT })
  objectInfo;

  @wire(getPicklistValues, {
    recordTypeId: '$defaultRecordTypeId',
    fieldApiName: PRIORITY_FIELD
  })
  wiredPriority({ data }) {
    if (data) {
      this.priorityOptions = data.values.map(v => ({ label: v.label, value: v.value }));
    }
  }

  get defaultRecordTypeId() {
    return this.objectInfo?.data?.defaultRecordTypeId;
  }

  get subjectError() { return this.errors.subject; }
  get priorityError() { return this.errors.priority; }
  get descriptionError() { return this.errors.description; }
  get disableSave() { return this.saving; }

  handleChange(event) {
    const field = event.target.name;
    this.values = { ...this.values, [field]: event.detail.value };
    // Clear the message for a field once the user edits it.
    if (this.errors[field]) {
      this.errors = { ...this.errors, [field]: undefined };
    }
  }

  async handleSave() {
    this.serverError = '';
    this.errors = validateCase(this.values);
    if (Object.keys(this.errors).length > 0) {
      return;
    }
    this.saving = true;
    try {
      const record = await createRecord({
        apiName: CASE_OBJECT.objectApiName,
        fields: {
          AccountId: this.recordId,
          Subject: this.values.subject.trim(),
          Priority: this.values.priority,
          Description: this.values.description
        }
      });
      this.dispatchEvent(new ShowToastEvent({
        title: 'Case created',
        message: 'Case ' + record.id + ' was saved.',
        variant: 'success'
      }));
      this.reset();
      this.dispatchEvent(new CustomEvent('saved', { detail: { id: record.id } }));
    } catch (error) {
      // Validation rules and triggers on the server end up here.
      this.serverError = readError(error);
    } finally {
      this.saving = false;
    }
  }

  reset() {
    this.values = { subject: '', priority: '', description: '' };
    this.errors = {};
  }
}
```

**force-app/main/default/lwc/quickCase/__tests__/caseRules.test.js**

```javascript
import { validateCase, readError, MIN_SUBJECT_LENGTH } from '../caseRules';

describe('validateCase', () => {
  const good = { subject: 'Printer will not start', priority: 'Low', description: '' };

  it('accepts a valid low priority case', () => {
    expect(validateCase(good)).toEqual({});
  });

  it('requires a long enough subject', () => {
    const errors = validateCase({ ...good, subject: 'short' });
    expect(errors.subject).toContain(String(MIN_SUBJECT_LENGTH));
  });

  it('ignores surrounding spaces when counting', () => {
    expect(validateCase({ ...good, subject: '   abc   ' }).subject).toBeDefined();
  });

  it('requires a priority', () => {
    expect(validateCase({ ...good, priority: '' }).priority).toBeDefined();
  });

  it('requires a description only for high priority', () => {
    expect(validateCase({ ...good, priority: 'High' }).description).toBeDefined();
    expect(validateCase({ ...good, priority: 'High', description: 'Details' })).toEqual({});
  });
});

describe('readError', () => {
  it('reads a UI API error array', () => {
    expect(readError({ body: [{ message: 'A' }, { message: 'B' }] })).toBe('A, B');
  });

  it('reads the output.errors form', () => {
    const error = { body: { output: { errors: [{ message: 'High priority cases need a description.' }] } } };
    expect(readError(error)).toBe('High priority cases need a description.');
  });

  it('falls back to message and then to a default', () => {
    expect(readError({ body: { message: 'Boom' } })).toBe('Boom');
    expect(readError({ message: 'Plain' })).toBe('Plain');
    expect(readError(null)).toBe('Unknown error');
  });
});
```

**force-app/main/default/lwc/quickCase/__tests__/quickCase.test.js**

```javascript
import { createElement } from 'lwc';
import QuickCase from 'c/quickCase';
import { createRecord } from 'lightning/uiRecordApi';

jest.mock('lightning/uiRecordApi', () => ({ createRecord: jest.fn() }), { virtual: true });

const flush = () => Promise.resolve();

function mount() {
  const element = createElement('c-quick-case', { is: QuickCase });
  element.recordId = '001000000000001AAA';
  document.body.appendChild(element);
  return element;
}

function fill(element, name, value) {
  const field = element.shadowRoot.querySelector(`[name="${name}"]`);
  field.dispatchEvent(new CustomEvent('change', { detail: { value } }));
}

afterEach(() => {
  while (document.body.firstChild) {
    document.body.removeChild(document.body.firstChild);
  }
  jest.clearAllMocks();
});

describe('c-quick-case', () => {
  it('shows validation messages and does not save an invalid form', async () => {
    const element = mount();
    element.shadowRoot.querySelector('lightning-button').click();
    await flush();
    expect(createRecord).not.toHaveBeenCalled();
    expect(element.shadowRoot.textContent).toContain('Subject needs at least 10 characters.');
  });

  it('saves a valid form with the account id', async () => {
    createRecord.mockResolvedValue({ id: '500000000000001AAA' });
    const element = mount();
    fill(element, 'subject', 'Printer will not start');
    fill(element, 'priority', 'Low');
    await flush();
    element.shadowRoot.querySelector('lightning-button').click();
    await flush();
    expect(createRecord).toHaveBeenCalledTimes(1);
    expect(createRecord.mock.calls[0][0].fields.AccountId).toBe('001000000000001AAA');
  });

  it('shows a server error such as a validation rule message', async () => {
    createRecord.mockRejectedValue({ body: [{ message: 'High priority cases need a description.' }] });
    const element = mount();
    fill(element, 'subject', 'Printer will not start');
    fill(element, 'priority', 'Low');
    await flush();
    element.shadowRoot.querySelector('lightning-button').click();
    await flush();
    await flush();
    expect(element.shadowRoot.querySelector('[role="alert"]').textContent)
      .toContain('High priority cases need a description.');
  });
});
```

## What happens behind the scenes

`lightning-record-edit-form` and `lightning-input-field` call the **UI API** for you. The UI API returns the object's metadata (field types, labels, picklist values, required flags, field-level security) together with record data, so the form shows only fields the user may see and renders the correct control for each type. When the user presses the submit button, the form posts the values to the UI API and the platform runs the full save: required checks, validation rules, triggers and sharing. If it fails, the error comes back in the response and `lightning-messages` displays it.

In layer 3 you take over the same conversation. `getObjectInfo` fetches the object's metadata, including its default record type id, and `getPicklistValues` needs that record type id to know which picklist values are valid. That is why `getPicklistValues` waits for `$defaultRecordTypeId`: the `$` prefix makes the adapter reactive, and it runs only when the value is defined. `createRecord` sends a UI API request and resolves with the new record's id.

The adapters share a **client-side cache** (Lightning Data Service). A second component asking for the same object info does not trigger a second network call, and a record updated through `updateRecord` refreshes every component that displays it.

The component's JavaScript decides **when** to ask the server. Client checks in `validateCase` run first and cost nothing; only a form that passes them is sent. The server then checks again, because client checks can be bypassed. Errors from the server may arrive in several shapes (an array, `body.output.errors`, or `body.message`), which is why `readError` handles all three.

## Test it and verify

1. Run `npm run test:unit` and confirm all tests pass.
2. Deploy, add the component to an Account page, and click **Create case** with an empty form; confirm each message appears.
3. Choose High priority, give a subject and leave the description empty; confirm the client rule appears. Remove the client rule temporarily and confirm the server validation rule message appears instead.
4. Log in as a user without Create on Case and confirm that the error is readable.
5. Open the browser's Network tab and confirm that picklist values load once.

## Common mistakes and fixes

- **Relying on client validation only.** Server rules still apply; show their messages.
- **Using `getPicklistValues` without a record type id.** Wait for `getObjectInfo`.
- **Mutating `this.values` in place.** Create a new object so the template updates.
- **Not handling the `catch`.** A rejected promise should show a message, not a console error.
- **Forgetting `lightning-messages`.** Edit-form errors vanish without it.
- **Hardcoding picklist values.** They go out of date; load them.
- **Missing permissions.** If a field is blank or absent, check field-level security.

## Key takeaways

- Start with the highest layer that meets the need: record form, then edit form, then adapters.
- Client checks improve experience; the server always has the last word.
- Reactive wires with `$` wait for their inputs.
- Keep rules in plain modules so they are easy to test.
- Test the invalid, valid and server-error paths.
